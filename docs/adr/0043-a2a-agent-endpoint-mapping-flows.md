# 43. Exposing flows as A2A agents: agent-card mapping and controls

Date: 2026-11-11

## Status

Accepted (2026-11-12). Not yet implemented. Protocol facts below were checked against the
Agent2Agent specification, version 1.0.0 (a2a-protocol.org, "Latest Released Version 1.0.0");
section numbers refer to that document. The implementation pins this version.

## Context

Flows are reachable as MCP tools through the Runtime's own MCP endpoint (`ALL /mcp`,
`createFlowMcpRouter`), with the same authorization as the chat API. There is no Agent-to-Agent
(A2A) endpoint and no agent card. The review asked whether ATF should speak A2A in addition to
MCP, and if so, how flows map onto agent cards and which controls apply to inbound tasks.

Relevant A2A 1.0.0 facts:

- The public Agent Card lives at `/.well-known/agent-card.json` (§8.2). An authenticated,
  richer card is available through `GetExtendedAgentCard` when
  `capabilities.extendedAgentCard` is true (§3.1.11, §4.4.3).
- Required card fields: `name`, `description`, `supportedInterfaces`, `version`,
  `capabilities`, `defaultInputModes`, `defaultOutputModes`, `skills`; optional among others
  `securitySchemes` and `securityRequirements` (§4.4.1). Endpoint and binding are declared per
  `supportedInterfaces` entry (`url`, `protocolBinding`, `protocolVersion`) (§4.4.6).
- A skill requires `id`, `name`, `description`, `tags`; optional `examples`, `inputModes`,
  `outputModes`, `securityRequirements` (§4.4.5).
- Bindings: JSON-RPC, gRPC and HTTP+JSON (§9–§11); an agent declares the ones it supports.
- Operations include `SendMessage`, `SendStreamingMessage`, `GetTask`, `ListTasks`,
  `CancelTask`, `SubscribeToTask`, push-notification configuration and `GetExtendedAgentCard`
  (§9.4).
- Task states: `SUBMITTED`, `WORKING`, `COMPLETED`, `FAILED`, `CANCELED`, `REJECTED`
  (terminal: the last four), `INPUT_REQUIRED` and `AUTH_REQUIRED` (interrupted) (§4.1.3).
- Security schemes follow the OpenAPI security scheme model (API key, HTTP auth, OAuth 2,
  OpenID Connect, mTLS) (§4.5.1); credentials travel in HTTP headers on every request (§7.3);
  the server authenticates every request (§7.4); production uses TLS (§7.1).
- Task ids are generated by the server; a client cannot create a task under its own id
  (§3.4.2). `SendMessage` *may* be idempotent; agents may use `messageId` to detect duplicates
  (§3.3.1).

## Decision

A thin A2A surface, built so that it adds no execution path of its own.

1. **Binding.** JSON-RPC over HTTPS first, at `POST /a2a` on the Runtime. gRPC and HTTP+JSON are
   not offered; the card declares only what exists.
2. **Two cards, no flow leak.** The public card at `/.well-known/agent-card.json` describes the
   deployment (name, description, interface, `securitySchemes`, capabilities) and lists **no**
   flow skills; it sets `capabilities.extendedAgentCard: true`. The authenticated
   `GetExtendedAgentCard` lists as skills exactly the flows the caller may run — the same filter
   as `GET /v1/models` and the MCP catalog, so the views cannot drift and unauthorized flows are
   never named.
3. **Skill mapping from flow metadata.** `id` → skill `id`; `name` → `name`; `description` →
   `description`; `["atf-flow"]` plus the flow's declared `dataClasses` → `tags` (the
   specification requires tags; data classes are the one classification a flow already
   declares); flow `requiredScopes` →
   skill `securityRequirements`. Input and output modes default to text; a flow with
   image input declares the image media types. No new flow field is introduced.
4. **Authentication reuses the chain.** `securitySchemes` declares OpenID Connect (the Runtime's
   issuer) and, where enabled, the managed API key as an HTTP bearer scheme. The A2A handler sits
   behind the same auth middleware as `/v1/*`.
5. **Translation only.** `SendMessage` → the chat pipeline (in-process, like `/v1/messages`,
   ADR 0038) with `origin: "a2a"`; `SendStreamingMessage` → the streaming path;
   `returnImmediately: true` → the existing async job path, and `GetTask` reads the job.
   Guardrails, the PII vault, budgets, admission, compliance rules, approvals, receipts and
   audit apply unchanged because the request runs through them.
6. **Deduplication.** The Runtime's idempotency key for an inbound message is
   `a2a:<tenant>:<messageId>`, so a resubmitted message reuses the existing run (the pattern of
   the Rocket.Chat channel). The task id is the run's execution id, generated by the server as
   the specification requires.
7. **State mapping.** queued → `SUBMITTED`; running → `WORKING`; waiting for a human approval →
   `WORKING` with a status message naming the pending approval (the approval is someone else's
   decision, not input the caller can give); finished → `COMPLETED`; refused by policy,
   compliance or authorization → `REJECTED`; budget exceeded or execution error → `FAILED`.
   `INPUT_REQUIRED` and `AUTH_REQUIRED` are not produced in the first iteration.
8. **Not offered in the first iteration.** `CancelTask` (answered with
   `TaskNotCancelableError`, because runs cannot be cancelled from outside today), push
   notifications (`capabilities.pushNotifications: false`), `ListTasks`, `SubscribeToTask`.
   Capability flags say so, and the specification requires the server to refuse calls to
   capabilities it does not declare (§3.3.4).

## Implementation plan

1. Runtime: `routes/a2a.ts` with the two card endpoints and the JSON-RPC handler, translating
   onto the chat router in-process; `A2A-Version` header handling; OpenAPI entry.
2. Tests: card content per caller (no unauthorized skill), `SendMessage` round trip,
   deduplication by `messageId`, state mapping, refusal of undeclared capabilities, and a
   conformance run against an A2A reference client pinned to 1.0.0.
3. Docs: CAPABILITIES (Channels), STABILITY (experimental until a second release confirms the
   mapping).

## Consequences

- Two protocol surfaces, one execution core. The invariant for review: the A2A handler contains
  no policy, no budget logic and no graph access — only translation.
- The version pin limits protocol churn to the translator; a new A2A version is a deliberate
  update, recognised by `A2A-Version`.
- Out of scope: outbound A2A (ATF calling other agents). It would need its own decision, because
  it raises egress-policy and delegation questions the egress guard has not seen yet.
