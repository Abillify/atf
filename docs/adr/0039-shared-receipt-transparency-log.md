# 39. Share the receipt transparency log between replicas

Date: 2026-11-11

## Status

Proposed

## Context

Decision Receipts are appended to an RFC-6962 Merkle transparency log
(`apps/runtime/src/receipts/transparency-log.ts`). The only implementation is
`InMemoryTransparencyLog`: leaf indices come from a process-local array
(`seq: this.entries.length`), the root is recomputed in memory, and sealed
tree heads live in a process-local list. A `ReceiptLogSink` interface exists
and Postgres implements it (`PostgresReceiptLogSink`,
`apps/runtime/src/receipts/receipt-log-sink.ts`, tables `receipt_log` and
`receipt_tree_heads` from migration 46, both protected by append-only
triggers) — but the sink is a write-behind copy, not the source of truth: the
tree an operator proves against is the one the local process built.

With `REPLICAS > 1` this diverges in two ways that break the receipt story:

1. **Leaf indices disagree.** Each replica numbers its own leaves from 0, and
   the Postgres `seq` (BIGSERIAL) interleaves appends from all replicas — so
   the in-memory `seq` and the durable `seq` for the same receipt are already
   different numbers on any multi-replica deployment.
2. **Tree heads disagree.** Each replica seals a head over its own subset, so
   an inclusion proof generated by replica A does not verify against a head
   sealed by replica B, and `atf-verify --receipt … --proof …` becomes
   replica-dependent.

The production gate says this out loud (`prod-gate.ts`: "the receipt
transparency log numbers its leaves and builds its tree per process, so
replicas produce diverging logs. Run receipt-issuing flows on one replica
until the log is shared"), and `docs/UPGRADE.md` lists it under "Not yet
shared between replicas". The consequence for scaling is real: the one
feature that makes receipts externally verifiable is the one that pins the
deployment to a single replica.

The audit log already solved the identical problem: `audit-log.ts` appends
under `pg_advisory_xact_lock(hashtext('atf:audit_log'))` inside one
transaction, "so two replicas never" race the sequence. That is the pattern
this ADR extends to receipts.

## Decision

Proposed: implement `PostgresTransparencyLog implements TransparencyLog`
behind the existing interface, with the database as the source of truth for
leaf order.

1. **Append under an advisory lock, in one transaction.**
   `append(receiptId, coseBytes)` runs, in a single transaction:
   `SELECT pg_advisory_xact_lock(hashtext('atf:receipt_log'))` →
   `INSERT INTO receipt_log … ON CONFLICT (receipt_id) DO NOTHING` (the id
   uniqueness the interface already promises: "Idempotent per receipt id") →
   re-read the row to obtain the authoritative `seq`. The BIGSERIAL `seq`
   becomes the leaf index — gaps cannot occur because the advisory lock
   serializes the whole insert, so BIGSERIAL advances exactly one per
   committed append. This is the same lock discipline as the audit chain
   (ADR 0026), applied to the receipt table.
2. **Tree head from the table.** `currentHead()` computes the root over
   `SELECT leaf_hash FROM receipt_log ORDER BY seq` — for the first
   implementation, a full recompute (the audit anchor cadence is minutes, and
   trees to ~10⁶ leaves recompute in well under a second; 2¹⁶ ≈ 65 k leaves
   is 16 SHA-256 levels). If profiling ever disagrees, an incrementally
   maintained node cache in a new `receipt_log_nodes` table is the described
   fallback — deliberately not built first, because a derived cache with its
   own consistency bugs is the classic transparency-log mistake.
3. **Sealing stays where it is.** `sealTreeHead()` keeps signing through
   `tree-head-sealer.ts` with the same COSE_Sign1 envelope over
   `[tree_size, root_hash, timestamp]`; only the head's input (root, size)
   now comes from the shared table. Sealed heads go to `receipt_tree_heads`
   as today. Because the table is shared, every replica seals the same head
   at the same size — duplicate seals at one size are harmless (idempotent
   content, extra rows) and a periodic sealer can run on every replica
   without coordination.
4. **Selection at wiring time.** Where the log is constructed, with a
   `DATABASE_URL` → `PostgresTransparencyLog`, without one →
   `InMemoryTransparencyLog` exactly as today (single-process deployments
   lose nothing). `ReceiptLogSink` remains as the write-behind interface for
   the in-memory class; the Postgres class implements `TransparencyLog`
   directly and does not need the sink.
5. **Migration for existing divergent logs.** Best-effort, documented as
   such: on first start of `PostgresTransparencyLog`, if `receipt_log`
   contains rows whose `(seq, leaf_hash)` ordering differs from any locally
   sealed head, nothing is rewritten (the table is append-only by trigger,
   and rewriting evidence would be worse than divergence). The new log
   continues from `max(seq)+1`. Receipts already issued keep verifying
   against the heads sealed before the switch — those heads and proofs are
   immutable artifacts and remain valid input for `atf-verify`. The
   migration is therefore "stop sealing on the old in-memory logs, start
   sealing the shared one", plus a runbook note that a deployment switching
   at `REPLICAS > 1` has, until then, per-replica log families — which is
   exactly what the production gate warned about, and the gate message
   changes to reflect the fix.

## Consequences

- **Formats are frozen where they matter.** The leaf hash (`H(0x00 ||
  cose_bytes)`), the tree-head encoding, the COSE_Sign1 envelope, and the
  proof format do not change — `docs/STABILITY.md` lists signature and
  receipt formats as stable surface, and this ADR honors that: only *who
  numbers the leaves* changes. Existing receipts and existing proofs verify
  with `atf-verify` unchanged; a fixture from the pre-shared format is part
  of the acceptance tests.
- **For operators:** the `REPLICAS > 1` production-gate warning for receipts
  disappears when the shared log is active (database configured), and
  `docs/UPGRADE.md` / `docs/runbooks/scaling.md` drop the "receipt-issuing
  flows on one replica" constraint.
- **For tests:** the existing property tests
  (`transparency-log.property.test.ts`) run unchanged against both
  implementations — that is the interface's job and the main regression net.
  New tests cover N parallel writers across two log instances against one
  database: gapless `seq`, one consistent head, inclusion proofs valid from
  the instance that did not append the leaf.
- **Risk — throughput:** the advisory lock serializes receipt appends
  deployment-wide. Receipt issuance is bounded by execution completion, not
  by a hot loop, and the audit chain carries the same pattern at higher
  volume; if receipt volume ever outgrew it, the escape hatch is batching
  appends per transaction (multiple leaves under one lock), which does not
  change the format.
- **Risk — restart semantics:** `InMemoryTransparencyLog.hydrate` exists
  because the in-memory tree must be rebuilt from the sink after a restart;
  the Postgres class has no such step (the table *is* the state), which
  removes a failure mode but also removes the ability to run with a
  temporarily unreachable database. Receipt issuance fails loudly when the
  database is down — correct for evidence, but it must be stated in the
  runbook.
- **Not decided here:** signed tree-head *publication* to an external
  witness (CT-style) or third-party checkpointing; the map of tenants to
  log partitions (one log for all tenants is the current and proposed shape,
  since leaves are already per-receipt and proofs reveal nothing about other
  leaves).
