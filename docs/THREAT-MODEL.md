# Threat model (STRIDE)

As of 0.19.0 (2026-10-22), in the state described by
the [CHANGELOG](../CHANGELOG.md). One section per service, grouped by STRIDE category, each row
reading threat → mitigation → residual risk. Port numbers are the host ports
of the Compose quickstart. Trust boundaries: (1) internet → gateway → Gate,
(2) Gate → internal services (network segment, service tokens), (3) Runtime
→ LLM and tool providers (egress), (4) Outpost → ATF cloud (dial-out; local
data stays local).

## Runtime (3000)

| Cat. | Threat | Mitigation | Residual risk |
| --- | --- | --- | --- |
| S | Prompt injection through documents or tools → data exfiltration via a tool call | Tool-authorization policy (ADR 0011), plugin trust boundary (ADR 0006), egress allowlist (`security/egress.ts`), red-teaming (ADR 0010); retrieved chunks are handed to the model as a delimited untrusted-data block with a per-call nonce (`RETRIEVAL_CONTEXT_MODE`, default `spotlight` in production); after the injection scan flags retrieved or tool text, tools not declared read-only (`readOnlyHint`) need human approval for the rest of the run (`TAINT_WRITE_TOOLS_REQUIRE_APPROVAL`, default on in production; tools without annotations count as write tools; without an approval gate the call is denied); Search marks retrieved content `content_trust: untrusted` with a heuristic `injection_risk` hint (`none` / `suspected`), and the Gate labels every tool result `_meta["io.atf/content-trust"]`; with `TAINT_MODE=on-untrusted-source` such content (and results of MCP servers without `contentTrust: trusted`) taints the execution, so consequential tools need approval | Model-inherent bypass ideas; detection stays heuristic and pattern-based, so `none` is not proof of safety; spotlighting lowers but does not remove the risk; the taint rule only protects tool calls routed through the node handlers, and does not cover consequential targets of the agent harness; the `injection_risk` hint is computed at query time, an ingest-time score is a possible follow-up |
| T | Tampered flow definitions or audit entries | Flow publishing is a regulated action on the fail-closed audit path; flows carry `metadata.version`, emitted as `flow_version` in the debug trace together with `flow_digest` (a hash of the executed definition, so a forgotten version bump is still visible) and `subflow_versions`; the audit log is hash-chained, append-only (migration 42) and anchored externally (ADR 0026) | Whoever compromises the deployment system and the database can forge both consistently; the anchor file must live off-host |
| R | Unauthenticated flow execution, BYOK abuse | Bearer/JWT on `/v1/*`, tenant isolation (ADR 0005), BYOK only per tenant, the production gate refuses auth-off | Insider with an admin token; admin actions are audited |
| I | PII in clear text at the provider or in logs | PII-vault decorator (ADR 0007), detector pipeline (ADR 0015), multimodal mode (ADR 0016), log redaction | New PII types need a detector extension; the fail mode is configurable |
| D | Expensive models or endless loops → cost DoS | Cost budgets and token limits (`BUDGET_*`, `observability/cost.ts` and `token-limits.ts`), FinOps forecast (ADR 0018), iteration and stagnation limits, rate limiting | Cost DoS below the budget threshold |
| E | Escalation: a tenant reads another tenant's data | RLS as a deployment option, application scoping, tests; one DB user per service | Application scoping without RLS is a known deployment decision (ADR 0005 status) |
| S | A second trusted token issuer asserts another tenant's identity | `JWT_ISSUER_TENANTS` binds every issuer in `JWT_ADDITIONAL_ISSUERS` to the tenants it may claim; an unlisted issuer or an unbound tenant gets 401 on `/v1/*` and the operator plane; the production gate fails with several issuers and no binding | A `"*"` binding trusts that issuer for every tenant; the binding is only as good as the map the operator maintains |
| T | Shadow or replay runs repeat real tool side effects | `suppressSideEffects`: the MCP wrapper refuses tools without `readOnlyHint`, approval-gated tools are denied without a reviewer, assistant memory writes are skipped; shadow sampling defaults to 5 % | A third-party MCP server that wrongly declares `readOnlyHint` on a write tool; `queryPreview` still keeps up to 256 characters of user text in memory |
| I | Credentials or tokens in service logs | A shared redactor (`@atf/security-kit` `log-redact`) runs on every Runtime, Search and Extract log entry; Gate redacts through the same kit; Search no longer logs queries, user ids or groups; OIDC logs carry a hashed email | Redaction is pattern- and field-name-based; secrets in free-form values of unusual shape can slip through; Search v1 still logs filter values |
| I | Operator credentials end up in the audit chain | The audit `actor` is the authorizer's resolved identity (token label / JWT subject) on every route that writes audit entries, including red-team and optimizer; a raw `Authorization` header or a token prefix is never written (regression-tested) | Rows written by versions before this change may hold a credential prefix; they cannot be removed without breaking the chain — rotate those tokens and restrict audit read access (UPGRADE, "0.18 → 0.19") |
| T | The audit chain or its anchor is rewritten after the fact | Hash chain over canonicalised `details` (stable across the Postgres `jsonb` round-trip, verified against a real Postgres), anchors signed with the Ed25519 evidence key (`EVIDENCE_SIGNING_KEY`, ADR 0030) or the legacy HMAC secret; the public key is published at `/.well-known/atf-evidence-jwks.json` | Only the current key is published; after a rotation, keep the old public keys to verify old artefacts. HMAC-signed artefacts need the shared secret |
| I | A figure embedded with `show_figure` is readable by anyone who holds its link | The tool runs only when `EMBED_SEARCH_FIGURES=true`, `MEDIA_BASE_URL` is set and the node declares `config.figureEmbedding` (`graph/figure-embedding.ts:19-22`); the bytes are fetched through the MCP `get_asset` tool with the caller's tenant/collection/row ACL, fail closed (`graph/figure-embedding.ts:8-12`); the link is a random v4 UUID with a TTL (24 h) and an LRU cap (100 entries) in an in-memory store (`graph/media-store.ts:76-79,102-103,116`); `GET /v1/media/:id` is deliberately exempt from API auth so a browser `<img>` can load it (`routes/media.ts:14-19`, `bootstrap/http-middleware.ts:153-156`) and answers `private` caching | The ACL is checked when the figure is fetched, not when the link is opened: whoever obtains the URL (chat transcript, proxy or access log, referrer) reads the image until it expires. The store is per process, so a link opened on another replica is a 404 (see [Not yet shared between replicas](UPGRADE.md#not-yet-shared-between-replicas-roadmap)). Embed deliberately chosen figures only |
| I | The data subject of an erasure stays in the erasure table in clear text | The identifiers are removed from the stored operation once it is `complete`; the signed receipt holds only pseudonymous hashes (sha256 of tenant id and identifier; not anonymous) | An operation that is not complete keeps them until a retry finishes it. Audit entries of erasure and policy decisions carry only hashes and HMAC pseudonyms keyed with `AUDIT_PSEUDONYM_PEPPER`; without the pepper the pseudonym is an unkeyed SHA-256 that anyone who guesses the identifier can recompute (the production gate warns), and entries written by earlier releases may hold the subject in clear text |
| R | A crashed erasure looks finished, or an erasure that reached no store is reported as done | Operations are stored `in_progress` with a lease and taken over after it expires; a request that addressed no store is `failed` | A run that died after erasing some stores is repeated in full — stores are deletion-idempotent |
| E | An invalid compliance policy switches enforcement off | A hot reload keeps the last valid policy; with none valid at startup chat and engine admission answer 503 | A deleted policy file still means "no policy"; `COMPLIANCE_POLICY_REQUIRED=true` makes a missing policy fatal in production (warning elsewhere); it is checked by the production gate at startup, and readiness reports `compliance_policy: missing` while a required policy is not loaded (also after a failed hot reload) |
| S | Similar-question cache hit returns an answer built from another user's sources or for a different question | Entries scoped to tenant and user; hit requires an identical context hash; only the last user message is matched; not part of the regulated presets | Answers to near-identical questions of the same user and context are served from cache for `SEMANTIC_CACHE_TTL_SECONDS` |
| T | A weak or tampered bench file yields a valid release receipt | The release receipt is signed with the evidence key (`signEvidenceBytes`, `EVIDENCE_SIGNING_KEY`) and bound to the flow digest and the bench file digest (`eval/flow-release.ts`); every executed case must report a debug trace whose `flow_digest` equals the local head, so a receipt cannot certify a revision the server did not run | A manipulated bench file committed to the repo produces a valid receipt for a weak test suite — bench files belong under code review like any other test asset |
| T | A cascade escalation repeats the first attempt's tool side effects | The escalation (`cascade.escalateTo`, `graph/cascade.ts`) re-runs the same input on the second model; the first attempt's held-back text is dropped, but its tool calls are not undone, so the documentation recommends the cascade only for nodes whose tools are read-only | An escalation on a node with write tools runs those side effects twice |

## Gate (3003)

| Cat. | Threat | Mitigation | Residual risk |
| --- | --- | --- | --- |
| S | Forged monitor sessions | Signed, HttpOnly session cookies (`mcpgate_monitor_session` for OIDC, `mcpgate_monitor_token_session` for the token exchange), optional OIDC login for the monitor with PKCE (S256), a `nonce` bound to the signed state cookie, `nbf`/`iat`/`azp` checks and a discovery `issuer` match; logout is `POST` only (`GET` answers 405) | — |
| I | The monitor stream exposes other tenants' events or tool results | An OIDC viewer sees only events of the session tenant (`monitoring.tenantScope: session`, default; events without a tenant are withheld) and tool results only as `meta.contentDigest` (SHA-256 and byte length, `monitoring.includeToolContent: false`, default); the session tenant comes from the verified tenant claim and the `tenantIsolation.issuerTenants` binding of the monitor issuer | `tenantScope: all` or `includeToolContent: true` restore the full view for every OIDC viewer; the static monitor token is the operator view and always sees all events |
| S | A second OAuth issuer asserts another tenant (tenant claim spoofing) | With tenant isolation on, `tenantIsolation.issuerTenants` binds every trusted issuer to the tenants it may assert (unlisted issuer 401, other tenant 403); the production gate makes an empty map fatal when more than one OAuth issuer is trusted and warns when `client_id` is used as a claim name | The tenant claim is whatever the IdP puts there: a claim a user can edit in the IdP is not a tenant boundary |
| T | An imported downstream tool is treated as read-only and skips write gating | Imported tools are `read` only when the downstream declares `annotations.readOnlyHint: true`, otherwise `write`; an explicit `access` wins | The hint is the downstream server's own claim; a server that declares it falsely is trusted as far as its operator is |
| E | The caller who triggered an action resolves its approval (no separation of duties) | The resolving identity is the verified caller (`ctx.subject`); `declaredApprover` is only a label. With `policies.approval.requireDifferentApprover` the approver must differ from the requester, belong to the same tenant and hold `approverScope`, and `verifyApproval` rejects tokens whose approver is the requester | The flag is off by default (production warns), approval tokens are HMAC-signed with a shared secret, pending approvals are per process unless Redis is configured |
| I | Bearer tokens and cookies cross the network in clear text | `http://` `server.publicUrl` / `monitoring.oidc.redirectUri` are fatal in `production`; cookies get `Secure` behind TLS | The Runtime → Gate and Gate → downstream hops are the deployment's network: terminate TLS or use an overlay network |
| I | Monitor token leaks through URLs, browser storage or script injection | `?token=` is refused on every monitor endpoint; the token is exchanged once at `POST /monitor/session` for an HttpOnly, SameSite=Strict cookie (8 h, invalidated by token rotation); the page is served with a nonce CSP (`frame-ancestors 'none'`) and no inline handlers | Scripts that still send `?token=` fail; a stolen cookie is valid until it expires or the token is rotated |
| T | Deleting or altering the Gate audit trail | The file audit sink (JSONL) applies a sink-level redaction policy; subject erasure only through `POST /v1/erasure` with the `gate.erasure` scope, idempotent over `requestId`; an append-only sink reports `not_configured` instead of erasing; the erasure operation itself is recorded in the Runtime audit chain (ADR 0025) | The JSONL file is not hash-chained; ship it to append-only storage if tamper evidence is required |
| R | Unauthorized MCP access | Bearer on `/mcp*`, tool policy at the Gate, `/.well-known/oauth-protected-resource` | An MCP client with a valid token can do everything it is allowed to (by design) |
| I | Metrics or health leak internals | `/metrics` only with `server.metrics.enabled`, health without details | — |
| D | SSE/session exhaustion | Session caps per transport and instance (`server.sessions`), per-identity GCRA rate limiting (memory or Redis), sticky routing documented (`runbooks/scaling.md`) | Slow clients hold slots |
| E | Erasure endpoint used as a weapon (mass deletion) | Service auth plus a dedicated scope, tenant binding, audit of every operation | Admin error; a four-eyes check in the process is recommended |
| E | The monitor playground used as a governance bypass (tools run out-of-band under a hardcoded identity) | Real runs go through the MCP dispatch pipeline (policy, approval, scopes, validation, rate limit, audit under the caller's identity); a dry-run needs the same scopes and obeys policy deny; HTTP dry-runs redact credential headers; an OIDC session keeps only its IdP scopes and a request-body `identity` is ignored; the production gate refuses `playground.enabled` and plaintext `publicUrl`/`redirectUri` | In static-token mode the monitor token is a root credential and the body `identity` is honoured by design; approval-required tools cannot be completed from the playground |
## Search (3002) / Extract (3004)

| Cat. | Threat | Mitigation | Residual risk |
| --- | --- | --- | --- |
| S | Query injection, path traversal in ingested files | Parameterized queries, path normalization, size and page limits (`MAX_PAGES`) | — |
| E | A writer publishes a document to readers of its own choosing (row-ACL override) | A principal that is a service or carries the scope `vectorsearch.acl.manage` may set a document's row ACL through `X-Allowed-Users` / `X-Allowed-Groups` (`apps/search/src/access-scope.ts:240-261`; the v2 revision API applies the same trust rule in `rowAclForRevision`, `:306`); a caller without that trust has its lists ignored and writes rows readable by its own identity and groups; Extract narrows the lists it forwards to its caller's identity, never widens | The service token is the ACL authority for everything it writes: whoever holds Extract's (or another indexing worker's) token can publish into any reader set of the collection. Scope the token per deployment and rotate it like a signing secret |
| T | Index poisoning (malicious documents) | Revisions and a delete path, tenant scoping, document ACLs | Poisoning within one's own tenant remains possible |
| R | Another tenant reads the index or documents | Mandatory access scope on every query (`ACCESS_SCOPE_REQUIRED`), service tokens between Extract and Search | — |
| I | Documents or PII in clear text in the Extract source store (`SOURCE_STORE_DIR`) or the Search asset store (`vs_assets` in the Search database, or `ASSET_STORE_DIR`) | Encrypted volumes (deployment responsibility), the erasure chain, converter isolation (ADR 0028) | Access to either store equals document access — volume and database hardening is required |
| I | Converted documents persist in the derived-PDF cache (`TEMP_DIR/derived-pdf`) | Deleting a document or an erasure removes its derived PDFs (`removeDerivedPdfsFor`); the cache is bounded by `DERIVED_PDF_CACHE_MAX_MB` (default 2048) and `DERIVED_PDF_CACHE_MAX_AGE_HOURS` (default 168); `DERIVED_PDF_CACHE=false` turns it off; on an `emptyDir`/tmpfs it disappears with the pod | The files sit unencrypted under `TEMP_DIR` |
| D | Conversion DoS (zip bombs, huge PDFs) | Zip-bomb guard before every unzip, `SUBPROCESS_TIMEOUT_MS` > 0 enforced, `MAX_PAGES`, per-job budgets (`BUDGET_EXCEEDED`), scratch quota | CPU exhaustion below the limits → scaling runbook |
| E | Converter escape (parser bugs in PDF/Office) | `CONVERTER_MODE=isolated`: separate process/container, only the socket and scratch space, non-root | Zero-day in a parser; isolation limits the damage |
| S | An HTML source makes the converter fetch internal URLs or read local files (SSRF, `file://`) | `neutralizeHtmlReferences` tokenizes the page and removes URL-bearing attributes, embedding elements, CSS `url()`/`image-set()`/`@import`, SVG data URIs and doctype subsets before LibreOffice sees it (regression-tested against known bypasses) | A deny-list: a reference type LibreOffice learns to load and the list does not name would pass. Run `CONVERTER_MODE=isolated`; in production `CONVERTER_MODE=local` is fatal unless `CONVERTER_ALLOW_LOCAL_HTML=true` acknowledges it (the Helm chart sets the acknowledgement by default) |
| T | A document carries instructions for the extraction model ("ignore the rules above …") | Text taken from a document sits inside `<rohtext>`/`<hinweise>`/`<beschriftung>`/`<dokumenttext>` elements, every system prompt says it is data, a literal closing tag in the text is broken, Unicode tag characters are removed; the output is parsed against a fixed structure | A model can still be swayed by content inside the fence; text that is invisible in the rendering but present in the text layer is passed on as text, and images are not scanned |
| I | Page content outlives the document in Extract (persisted model responses, outboxes, upload files, source bytes) | `DELETE /v2/documents/{reference}` and `POST /v1/erasure` remove the jobs (checkpoints and outboxes cascade), upload sessions and unused source bytes; `JOB_RETENTION_DAYS` and `UPLOAD_SESSION_MAX_AGE_HOURS` bound the rest; the production gate warns while no job retention is set | Source bytes are kept while the document is served (`/v2/render` needs them) and leave only with the document or an erasure; retention is off until `JOB_RETENTION_DAYS` is set |
| S | Answer-ready retrieval hands injected document text to an answering model (`retrieve_for_answer` / `/v2/retrieve`) | The response marks every passage `content_trust: "untrusted"` (`retrieve-for-answer.ts`) and the caller's ACL applies to each candidate like in search; the token budget bounds how much text one call packs (`packEvidence`); the Runtime-side injection scan, content-trust labels and taint (`TAINT_MODE`) apply to the passages as to any retrieved content | Prompt injection inside an evidence passage; detection stays heuristic (see the Runtime prompt-injection row) |
| I | `trace` / `document_diff` expose superseded or deleted content of earlier revisions | Both tools run the same access scope as search — the mandatory access scope plus the temporal "version valid at that instant" rule (`valid_at`) on the caller's token (`handlers/mcp-trace-tool.ts`, `handlers/mcp-document-diff-tool.ts`) | A user who may read the document sees content of earlier revisions — replaced or deleted ones included — as long as those revisions are stored; removal runs through erasure or revision TTL |

## Outpost — Docker runtime

| Cat. | Threat | Mitigation | Residual risk |
| --- | --- | --- | --- |
| S | Malicious sync targets (cloud) write harmful files into mounted folders | Read-only mounts where possible, confirm-deletes flow, the Outpost only ingests with a tenant token | Local consumers of the folders (Office) open harmful files — OS hardening is required |
| T | Outpost configuration tampered with (other cloud targets) | Read-only config mount, audit on the ATF side for every ingest | Whoever controls the host controls the sync — the Outpost runs on customer infrastructure |
| R | A stolen Outpost token uploads foreign data | Tenant-bound token, rotation like service tokens, interactive source login (`source-login`) | Token in the container environment — a secret store is recommended |
| I | Local data leaves the host unencrypted | TLS to ATF, health endpoint bound to 127.0.0.1 by default | Network segment behind the Outpost |
| D | Sync storm (wave of changes) | Backoff and rate limiting in the core, delta sync | — |
| E | The Outpost becomes a lateral-movement hop | Non-root user (UID 10001), no Docker-socket mounts, minimal capabilities | Host escape as with any container |

## Outpost Desktop + updater

| Cat. | Threat | Mitigation | Residual risk |
| --- | --- | --- | --- |
| S | A compromised updater feed ships a malicious binary | Mandatory signatures (Minisign public key in `tauri.conf.json`); endpoints stay empty until the release infrastructure exists, so **the updater is currently disabled** (`createUpdaterArtifacts: false`); a signed release build in `outpost-release.yml` fails on the placeholder key or empty endpoints | The public-key rotation process must be anchored in the release workflow before the updater is enabled |
| T | Binary tampering between build and install | Digest pinning, SBOM, image and artifact scans in CI; desktop builds from reviewed commits | Supply chain of the Tauri/Rust dependencies (`deny.toml`) |
| R | The sidecar (`atf-outpost`, `externalBin`) is reachable without UI auth | Sidecar bound to localhost, per-launch IPC token handed to the WebView by the app | A local process sniffer running as the same user |
| I | Cloud OAuth tokens on the desktop | OS keychain instead of a file, refresh rotation | Same OS user = same access (OS model) |
| D | Sync blocks the UI | Sync runs in the sidecar process, not in the UI thread | — |
| E | The desktop app escalates privileges | Minimal Tauri capabilities, no shell access from the WebView | Tauri zero-day |

## Cross-cutting

- **Secrets**: never in the image; secret store plus the production gate,
  which refuses auth-off and demo secrets in production.
- **Supply chain**: CI with a lockfile check, Trivy (fails on critical CVEs),
  gitleaks, CodeQL, SBOM (`sbom.cdx.json`), cosign-signed release images
  with provenance and SBOM attestations, Actions pinned by SHA.
- **Audit**: every regulated action (erasure, key rotation, policy changes,
  approvals, flow publishing, tenant deletion) goes through the fail-closed
  Runtime audit path into the hash chain.

Review triggers: new services, new provider egress classes, enabling the
updater, and at least once a year.
